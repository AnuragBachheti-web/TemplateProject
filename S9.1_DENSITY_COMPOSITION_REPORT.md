# Action Stories — Visual Density & Composition Pass

Follow-up to `S9.1_ARCHITECTURE_FIX_REPORT.md`, against the supplied Realify reference image and
`FORENSIC_AUDIT_S9.1.md`. That pass fixed *where* content goes (region/section/grouping). This pass
fixes *how much space* it's given once it's there — the remaining "card-wall, too vertically tall"
complaint was real, and distinct from the semantic-placement bug already fixed.

**Honesty check up front:** no live browser/screenshot was available in this environment (checked
again this turn). Every claim below is verified by (a) reading the actual JSX each block now
renders, (b) real jsdom/react-dom renders in tests (not shallow calls) that assert on the resulting
class names and DOM shape, and (c) a full-corpus scan of all 26 workflows' real data run through the
new logic. That is real, load-bearing verification — it is not a pixel-level visual comparison, and
I am not claiming one.

---

## 1. What caused the remaining excessive height

Four distinct, provable causes — the semantic-placement fix from the prior pass did not touch any
of these:

1. **A rich, uniform, multi-column labeled record (`policy`: `{label, value, current, why}`) was
   classified `labelValueList`**, whose per-row rendering shows `label`+`value` on one line, then
   `current` and `why` each on their *own* additional line beneath it — roughly 3 lines per record.
   The identical information as an actual table is 1 row. Three policy rows: ~9 stacked lines vs. 3
   table rows.
2. **A hero-role text block's rich "Realify signal" card treatment ignored `compact`.** Once the
   prior pass correctly grouped `rationale`/`heroTitle`/`heroSub` into a shared panel, the block
   itself still drew its *own* full bordered card inside that shared panel — a literal card nested
   inside a card, adding a full border+padding+shadow layer for no informational reason.
2b. **`heroSub` reused the exact same "Realify signal" eyebrow as `heroTitle`**, so a headline+
   subheadline pair showed the identical eyebrow label twice, stacked, for one story beat.
3. **A list where every item reduces to a single field (`{name, hue}}` — a color-legend, e.g.
   `roles` on Analyze) rendered as N full-width bordered `<li>` rows, stacked vertically** — the
   "six large stacked pills" the reference calls out. The data has no more than a label and a color
   per record; six independent bordered rows for that is pure overhead, not information.
4. **A chart's height was one fixed value (`h-56`, 224px) regardless of context** — a chart sharing
   a dense composed panel with a headline and a move-mix bar was given the exact same vertical
   budget as a chart standing alone as a stage's one featured visual.

None of these are CSS-only problems — each is a **composition/classification** decision (which
`blockType` a shape gets, whether a block treatment respects its container, what "simple" data
deserves) that happened to *manifest* as excess whitespace.

## 2. Which composition rules were changed

- **Classifier (`extraction/classifyBlocks.js`)**: a uniform, all-scalar, labeled row set now
  promotes from `labelValueList` to `table` once it has **≥4 meaningful columns** (a stricter bar
  than plain `table`'s ≥3, so a simple 2–3 field checklist is untouched) — with one explicit,
  vocabulary-keyed exemption (`CHECKLIST_RAW_KEYS = {'checks'}`) for the one confirmed case where a
  rich labeled row set still reads better as a compact rail checklist than a table (a live
  guardrail pass/fail gate).
- **`heroSub` gets its own role** (`role: "heroSub"`), distinct from `heroTitle`'s `role: "hero"` —
  a paired subheadline is never itself a headline, so it never draws an eyebrow/card of its own.
- **Every block that can end up inside a shared panel now respects `compact` and skips its own
  card** in that case: `TextBlock`'s hero treatment, `TableBlock`, and (already done in the prior
  pass) `BarChartBlock`.
- **`ItemQueueBlock` gained a data-driven "uniformly simple" check**: when *every* item in a list
  reduces to nothing but a headline (no detail/identifier/state/severity/nested-list/extra-field),
  it renders as a wrapped row of compact chips instead of N stacked bordered rows. A list with even
  one richer item is completely unaffected (falls through to the existing per-row treatment
  unchanged) — this only fires where collapsing loses zero information.
- **`BarChartBlock` gained a content-driven height tier**: `h-32` (128px) when `compact` (sharing a
  panel), `h-56` (224px) when standalone (a stage's one featured chart).
- **Composition-level spacing tightened** (page/section/row gaps only — component-internal padding
  was left alone, since the height problem was never really "cards are too padded," it was "there
  are more/taller cards than the information warrants").

## 4. New layout/density metadata

None was added beyond what the prior pass already introduced (`role`, `region`, `layout.group`,
`layout.span`). This pass deliberately did **not** add a `density`/`size` field to the manifest
schema — every density decision made here derives from data the manifest/block already has
(column count, item shape uniformity, `compact` context), not a new authored dial. This is a
narrower scope than the "layout.density / layout.size" schema sketched in the request, and that
narrowing is a real, honest trade-off: fewer schema concepts to maintain, at the cost of no
per-block manual override for a future case these shape-driven rules don't cover. If a future case
needs an explicit override, it composes cleanly on top of what exists (an optional `block.density`
would slot in next to `role`/`region` the same way).

## 5. How the generic composition engine works (unchanged shape, refined rules)

```
raw data
  → classifyBlockType (shape, now including the table-promotion rule)
  → planSections (role/region/section, now including heroSub's distinct role)
  → composeSections (region resolution, grouping — unchanged this pass)
  → StageSections (GridPanel / ComposedPanel / RailPanel — unchanged this pass)
  → block component (now respects `compact` consistently: Text/Table/BarChart/ItemQueue all skip
    their own card when already inside a shared panel; ItemQueue additionally collapses truly
    simple lists into chips)
```

The composition *layer* (where content goes, what it's grouped with, how much width) is untouched
from the prior pass — this pass only changed **classification** (is this shape a table or a list)
and **block-level compactness discipline** (does this block draw its own card when it shouldn't).

| | Before this pass | After this pass |

| Reason: `policy` | `labelValueList`, 1 card, ~9 stacked lines (3 records × 3 lines each) | `table`, 1 card, 3 rows, 1 line each |

reduce *panel count* further, it reduced the **content height inside** the panels that were
disproportionately tall for their information (policy, and the hero-in-hero nesting). Analyze's
`roles` panel count also stayed at 1 (it already was one card) — its *internal* height dropped
roughly 6:1 (six stacked rows → one wrapped row).

## 10. Remaining visual gaps (named honestly)

- **No live screenshot verification** — stated above and repeated here per the task's explicit
  instruction not to claim pixel-level validation without it.
- **The reference image's "Suggested Outcome," "Assortment Capital" donut-by-role, and per-metric
  sparklines have no corresponding field in the real S9.1 data** (verified against the actual raw
  fixtures, not assumed) — these were not fabricated to chase the image. This is a real,
  data-availability gap, not a composition-engine gap; inventing that content would violate "no
  silent data loss / no fabricated content" more than it would help.
- **The reference's top-row "3 independent cards side by side" pattern for Reason (Rationale /
  Display Mode / Suggested Outcome) is approximated, not replicated exactly** — `rationale` and
  `display_mode` now share ONE panel (bare content, a vertical divider between cells) rather than
  each keeping fully independent shadowed boxes in a row. This is a deliberate, scoped trade-off
  (documented, not hidden): building a true "row of independent cards" composition primitive beyond
  the existing GridPanel/ComposedPanel/RailPanel set was judged out of scope for this pass.
- Several Decide-stage rail microcopy fields (`focusTitle`/`focusMeta`/`focusFooter`, flagged in the
  prior report) still sit in the generic "Summary" rail bucket rather than attached to the
  main-column widget they actually caption — unchanged by this pass, same reasoning as before (not
  yet a confirmed cross-workflow vocabulary pattern, so not generalized).
- Chart height tiering only has two tiers (compact/standalone) via the existing `compact` boolean,
  not a richer `size: small/medium/large` scale — judged sufficient for the concrete cases in real
  data today; a genuinely "featured, larger-than-standalone" chart doesn't exist in the current 105
  fixtures to justify a third tier.

## 11. Explicit status

**Structurally faithful and materially denser than before, but not independently pixel-verified
against the reference image** — the composition/classification fixes are real, tested, and proven
against all 26 workflows' actual data (not just S9.1), and the specific complaints named in the
task (policy-as-list, roles-as-pills, hero-card-in-a-card, one fixed chart height) are each
fixed with a cited, generic, data-driven rule. What is *not* claimed: that the rendered page now
matches the reference image pixel-for-pixel, or that every one of the reference's illustrative
elements (sparklines, the capital-by-role donut, "Suggested Outcome") now exists — those require
data this application doesn't have, not a further composition-engine fix.
