# Action Stories — Semantic Composition Architecture Fix

Implements the fixes prescribed against `FORENSIC_AUDIT_S9.1.md`, using S9.1 as the canonical proof
case. No workflow-specific JSX conditionals were introduced anywhere in the renderer.

---

## 1. Root cause

The reference cannot be reproduced by "add more CSS." The pipeline (extraction → classifier →
manifest → composition → renderer) loses or never captures **semantic** information at three
specific, provable points:

1. **`sectionIdFor()` derived a block's placement from its *blockType shape*, not its meaning.**
   A scalar `text` block was *always* routed to a "summary" bucket, and every consumer then treated
   "summary" as inherently secondary/rail content, for every workflow. Concretely: S9.1 Decide's
   `heroTitle`/`heroSub` — the reference's own dominant, main-column recommendation headline —
   classified as scalar `text` → "summary" → the 300px rail, indistinguishable from a button label.
2. **The manifest had a real grouping mechanism (`layout.group`/`layout.span`) that was never
   populated.** Nothing told the renderer that `heroTitle` + `heroSub` + `heroMetrics` + `moveBar`
   are one composed panel in the reference — they were four independent blocks in four different
   inferred buckets.
3. **The Action Story's own per-instance headline was never extracted at all.** It lives in the
   reference mockup's static banner markup, not inside the `renderVals()` script the extraction
   tool parses — a real, confirmed, silent data-loss bug, not a classification issue.

Everything else about S9.1's actual content (metrics, tables, charts, guardrail rules, decision
data) was already present, unmangled, in the raw fixtures — this was never primarily a
missing-data problem.

## 3. Architectural changes — the new semantic/layout contract

All fields below are **optional and additive**. A manifest with none of them behaves exactly as
before.

```
block: {
  slotName, blockType, binding,      // unchanged, required
  section?,                          // unchanged — which section this block belongs to
  role?: "hero",                     // NEW — semantic weight, independent of blockType
  region?: "main" | "rail",          // NEW — a single block's own placement override
  layout?: { group?, span? },        // unchanged field, NEW domain: span is 1–12 (was 1–3)
}

section: { id, title, region? }      // NEW: region ("main"|"rail") — declarative, not inferred
```

**Region resolution order** (`composeSections.js`, fully documented in its own header comment):
1. `block.region` — a single block overriding its own placement.
2. `section.region` — the section declaring where it belongs, once.
3. The **old** name-based guess (`guardrails`/`summary` ⇒ rail) — the fallback for any manifest
   that declares sections but no `region` at all.
4. `"main"` — the always-safe default (matches every prior unsectioned-block behavior).

**Composition primitive (Fix #7):** `StageSections.jsx` now renders a `grid`-type row two ways,
distinguished by *origin*, not content:
- **heuristic** (composeSections' own scalar/small-object adjacency fallback) → the existing
  `GridPanel` (a tight metric strip, unchanged visual treatment, zero regression risk).
- **explicit** (a manifest-declared `layout.group`) → the new `ComposedPanel`: a vertical stack,
  each member spanning its own declared width out of a 12-column grid, no block needing to know
  it's inside one (block components stay "dumb" — they answer "how do I render this data";
  `ComposedPanel` answers "where does this belong and what does it belong with").

**Semantic vocabulary added to `classifyBlocks.js`'s generation-time rules** (vocabulary-keyed by
raw key/slotName, never by workflow code — see the file's own doc comments for the exact table):
`heroTitle`/`heroSub`/`rationale`/`primaryInsight` → `role: "hero"`, section `recommendation`
(`region: "main"`); their companions `heroMetrics`/`moveBar`, when a hero slot is present in the
same stage → same section/group; `totals` → new `rollup` rail section ("Totals"); `basis` → new
`provenance` rail section ("Basis").

**Identity:** `manifest.headline` (and `data/index.json`'s own `headline`) is now a field distinct
from `name`, sourced from `extractInstanceHeadline()` reading the reference's own per-instance
banner text — never fabricated when absent.

## 4. S9.1 result — exactly how the reference composition is now represented

Verified by running the real, regenerated pipeline (not hand-edited) through `composeSections`
directly:

**Decide** (the audit's primary example):
```
MAIN
  recommendation (no header, matches the reference's own hero card having none)
    [COMPOSED PANEL] heroTitle(12) → heroSub(12) → heroMetrics(12, chart) → moveBar(12, list)
  details ("Details")
    [single] slates       [single] groups        [single] focusRows

RAIL
  guardrails ("Guardrails")   — guardrail_checks, guardrail_blocked/can_approve/cta_label
  summary ("Summary")         — remaining scalar microcopy (see §7)
  rollup ("Totals")           — totals
  provenance ("Basis")        — basis
```
This is a structural match to the reference's actual composition: the hero headline, subtitle,
metrics, and move-mix bar render as one shared panel in the main column; the rail is now 4
distinct cards (vs. the reference's 4) instead of 2 undifferentiated ones, and none of them
contain the recommendation headline anymore.

**Reason/Analyze/Execute:** structurally unchanged (Reason/Analyze are below the 9-block
sectioning threshold and were never affected by the rail-misplacement bug; Execute has no
hero-vocabulary slot) — confirmed by the same direct pipeline dump, no regression.

**Generalization (Fix #6):** regenerating via the real pipeline (not a hand-edit) shows this isn't
an S9.1 special case — **20 of 26 workflows** now get a `recommendation` main-region section where
they previously had none, and **14 of 26** get the new `rollup` rail section. `provenance`
currently fires only for S9.1 (the raw key `basis` doesn't recur elsewhere in the dataset today) —
declared by vocabulary regardless, so it activates automatically wherever that key appears.

## 5. Backward compatibility

- **Every one of the 105 real stage manifests was regenerated through the actual pipeline** (not
  hand-authored) and re-validated: `0` slot-name collisions, `0` self-check problems, `0`
  `validateManifest()` problems, **1760 blocks generated — identical to the pre-change count**
  (nothing dropped, nothing invented).
- `manifestFixtureSweep.test.js` sweeps all 105 stage manifests end to end (resolve → validate →
  compose) and asserts zero orphaned blocks and that composition accounts for every block exactly
  once across *both* regions — this passes.
- The region-resolution fallback chain (§3) means a manifest with `sections` but no `region` field
  renders exactly as it did under the old `RAIL_SECTION_IDS` name-based guess; a manifest with no
  `sections` at all renders exactly as it did as one unsectioned main-region bucket.
- `layout.span`'s old domain was 1–3; it's now 1–12. No real manifest declared `layout.span` before
  this change (confirmed: 0 of 1,760 blocks), so this is not a behavioral change for any existing
  data, only for the newly-authored `recommendation` groups.

## 8. Remaining gaps (genuinely outside this task's scope)

- `focusTitle`/`focusMeta`/`focusFooter` (Decide) still land in the "summary" rail bucket, even
  though in the reference they're captions *inside* the main-column "Focus" panel, not rail
  content. This is the same *class* of bug as the hero misplacement, but recognizing it generically
  (a caption-triple pattern paired with a `focusRows` table) isn't yet confirmed as a cross-workflow
  vocabulary the way `heroTitle`/`totals`/`basis` are — flagged, not solved, to avoid inventing an
  unverified generic rule.
- No "Held out of the exit pool" rail card — no raw fixture field maps to it; nothing to bind.
- Reason/Analyze stages (and any stage under the 9-block threshold) still get no rail at all — a
  pre-existing limitation, not part of this fix's target and not worsened by it.
- Only `BarChartBlock` gained a `compact` mode. A future `layout.group` mixing in a table,
  itemQueue, or another chart type would still show a nested card until those components get the
  same small addition — noted, not implemented, since S9.1's proof case only needed this one.
- `S10.3`/`S10.6` had one stage each whose banner is templated (`{{ ... }}`) rather than a static
  literal; the new extractor detects and skips that (never leaks raw template syntax), so those two
  workflows' headline comes from whichever of their other stages has a real literal — correct
  behavior, but means their `headline` isn't drawn from every single stage the way S9.1's is.

## 9. Regression risks

- **All 26 workflows' manifests changed** (confirmed via `git diff --stat`); only S9.1 was manually,
  structurally inspected in this depth. The automated sweep (0 orphaned blocks, 0 validation
  problems, block count unchanged at 1760) is strong evidence nothing broke, but a follow-up visual
  pass across the other 19 workflows that gained a `recommendation` section would be the honest next
  step before calling this "verified" everywhere, not just "not broken."
- The headline-extraction mustache guard (`/\{\{.*\}\}/`) is a new heuristic; a real headline that
  legitimately contained literal `{{`/`}}` text would be incorrectly suppressed — no such case
  exists in the current 105 fixtures (checked), but it's a theoretical edge case worth knowing about.
- `--page-max` moved from 1280px to 1320px — a real, if modest, visual change, reasoned from the
  reference's own content-area math (§9 of the token's own comment), not an arbitrary tweak; still
  worth a design-review glance since it does touch every stage page.
