Realify Dynamic Template System

How one JSON template plus one JSON runtime payload become a rendered workflow stage — and exactly which half of that the backend owns. Everything below is extracted from the action-stories feature in this repository: real manifests, real fixtures, real component names, real binding paths, real action definitions.

Corpus today
26 workflows

105 stage manifests, 105 runtime fixtures, rendered by 14 reusable block components and one renderer.

What is real

The template schema, the binding resolver, the validators, the block registry, the renderer, the action schema and the action bar are all shipped code with tests.

What is not

There is no live backend. Runtime data is read from local JSON files; actions persist to localStorage. Every such spot below is tagged currently mocked.

How to read the tags. current shipped and running in the app today · currently mocked real code path, no real backend behind it · target contract schema exists but nothing uses it yet, or proposed for the backend · simplified for demonstration this standalone page approximates something the React app does more fully.
This page is a standalone re-implementation. The React app renders these exact manifests and fixtures through React components. This file has no React and no network access, so the renderer below is a faithful but simplified vanilla-JS port: resolveBinding, evaluateCondition, the 14 block-type validators and resolveActionState are ported logic-for-logic; the visual output of each block and the section/row layout heuristics are approximations. The contract is exact; the pixels are not.

The one sentence that matters

The renderer contains zero business vocabulary. It does not know what "repricing", "guardrail" or "approve" mean. A stage looks the way it looks because a manifest said blockType + binding, and it behaves the way it behaves because a manifest said actions[] + when. Both are data. Adding a 27th workflow requires no renderer change.

        Important honesty note for the backend. These fixtures were machine-extracted from
        static HTML mockups (extraction/*.js), so data currently carries three kinds of
        field a real API should not send:
        
    
          
  • Presentation fields — bg, tone, tint, border, hue, edge, srcTint… usually holding CSS like var(--green-700).
    • 
          
  • Geometry fields — bandLeft, dotLeft, newLeft, x, cy, top, height — pixel/percentage positions from the mockup.
    • 
          
  • Internal companions — __raw, extraction's copy of a row's unformatted numbers.
    •

        are invisible in the UI. The target contract is: send business values only. Colour is derived
        client-side from a value's own sign/wording (blocks/deltaTone.js), never from an API-sent colour.
      


      

        Also worth knowing. Most numbers arrive today as pre-formatted display strings
        ("$1.86", "−1.24", "88% ± 5") because a mockup had no other form. The blocks
        accept both strings and numbers. INTEGRATION.md already records that the real proposal API returns
        typed numeric fields (e.g. impact_minor in minor units) — mapping those to display strings is an
        open design question, not a solved one. needs a decision

Data Binding — template path → runtime value → rendered UI

  

    Live traces, computed in this page by the ported resolveBinding against the real
    S9.11/analyze fixture. Each row is one real block from the real manifest.
  


  

    

      
manifests/resolveBinding.js — the whole resolverreal code

      
export function resolveBinding(binding, data) {
  if (typeof binding !== 'string' || binding.length === 0) return data

  const path = binding
    .replace(/\[(\d+)\]/g, '.$1') // "rows[0]" -> "rows.0"
    .split('.')
    .filter((segment) => segment.length > 0)

  let current = data
  for (const key of path) {
    if (current === null || current === undefined) return undefined
    if (typeof current !== 'object') return undefined
    current = current[key]
  }
  return current
}

    

    

      

        Guarantees the backend can rely on.
        
    
          
  • Resolution never throws. A missing key, a null mid-path or an out-of-range index all resolve to undefined.
    • 
          
  • undefined ⇒ that one block renders a visible placeholder and logs a warning. The rest of the stage renders normally.
    • 
          
  • The resolved value is passed to the component byte-identical — no coercion, no formatting, no default.
    • 
          
  • Bracket indices are supported: data.rows[2].name.
    • 
          
  • A present but wrong-shaped value is what fails validation — absence alone never is.
    • 
        

      

      

        Optional fields are a first-class case. If your endpoint legitimately omits a field,
        nothing breaks. Dataset B in §7 omits data.excluded entirely and the other 7 blocks render
        untouched — that behaviour is asserted by a committed test
        (manifests/templateReuse.e2e.test.jsx).

        52 declared actions, and every single one is { id: "confirm", kind: "primary", action: "confirm" }
        — one per decide/execute stage, generated by

Action schema — validateManifest.js

      

        

          
FieldStatusMeaning

          
            
id requsedUnique within the stage. Keys the pending/done/error state as ${code}/${stageKey}/${id}.

            
label requsedButton text.

            
kindprimary onlyprimary | secondary | destructive. Only primary appears in real data.

            
actionusedBackend operation type, distinct from id. Selects the handler in ACTION_HANDLERS. Defaults to id.

            
whenusedEligibility condition over the runtime payload. Absent ⇒ always enabled.

            
labelBindingusedBinding whose string value overrides label (e.g. "Approve 4 moves & continue").

            
disabledReasonBindingusedBinding read only when when fails — the backend supplies the human explanation.

            
confirmused{ required?, title?, description? } → modal before dispatch.

            
reasonunused{ required?, label?, minLength? } → free-text capture in the modal, validated client-side, sent as reason.

            
loadingLabelunusedButton text while pending; defaults to "<label>…".

          
        

      

    

  


  
The when condition language — manifests/actionCondition.js

  
Deliberately not a general expression language: no arithmetic, no string ops, no user code, nothing that can loop or throw. The same language gates blocks[].when.

  

    

      

        Operators
        
opneeds valuewhen the path resolves to undefined

        
          
eq gt gte lt lte inyesfails — you cannot claim a value you don't have

          
ne notInyespasses — absence is not itself a block (fail-open)

          
existsnofails — the explicit opt-in to fail-closed

          
notExistsnopasses

          
truthy / falsynoBoolean(undefined) ⇒ falsy

          
{ all: [...] } / { any: [...] }—recursive AND / OR

        
      

    

    

      

        Why ne and not eq in the real manifests. The generated guardrail gate is
        { all: [ {path:"data.blocked", op:"ne", value:true}, {path:"data.canApprove", op:"ne", value:false} ] }.
        Because ne treats a missing value as satisfying the condition, a backend that simply
        doesn't send blocked/canApprove leaves the action enabled. That is deliberate:
        it reproduces the pre-existing rule "absence of guardrail data is not itself a block". If you want a
        field's presence to be required, the manifest must say exists explicitly.
      

      

        What this means for you. Eligibility is a backend-owned business rule expressed as
        frontend-readable data. You decide blocked/canApprove; the manifest decides how to
        read them; the renderer decides nothing. Server-side authorisation must still be enforced on the
        action endpoint — when is a UI affordance, never a security boundary.

Frontend vs Backend Responsibilities

  

    

      
Frontend owns

      
    
        
  • The template / manifest — manifests/*.json, versioned in the frontend repo, not served by any API. current
    • 
        
  • The block vocabulary — which 14 blockTypes exist and what each expects.
    • 
        
  • Binding declarations — which path feeds which block.
    • 
        
  • Layout — sections, main/rail regions, row grouping, spans, compact vs card.
    • 
        
  • Action presentation — labels, ordering, confirmation copy, reason capture, loading/retry/done states.
    • 
        
  • Shape validation — validateManifest + the 14 validate<Type> functions.
    • 
        
  • Client UI state — sort, pagination, slider position, dialog open, toasts, theme.
    • 
        
  • Error presentation — every raw error becomes a safe userMessage.
    • 
      

    

    

      
Backend owns

      
    
        
  • The whole data object — every business value, row, metric, status and label in it. today: local files
    • 
        
  • Collection contents and lengths — how many rows, how many checks, which SKUs.
    • 
        
  • Resource state — what stage this workflow is in, what has been approved.
    • 
        
  • Eligibility facts — the values when reads (data.blocked, data.canApprove).
    • 
        
  • Human explanations — the string behind disabledReasonBinding, and the CTA behind labelBinding.
    • 
        
  • Authorisation — enforced on the action endpoint. no endpoint yet
    • 
        
  • Action execution and its result — the real mutation. currently localStorage
    • 
        
  • Post-action state — what the stage looks like afterwards. not implemented
    •

Section 14

  
Backend Integration Notes


  
The minimum to make this real

  
    
    
  1. Serve the data object. Everything else already works. One endpoint returning
      { code, stageKey, name, headline, data } for a given workflow+stage replaces the entire fixture
      layer. props and state can be dropped — nothing reads them.
    2. 
    
  2. Keep the field names. Bindings are literal paths. data.rows must be called
      rows. Renaming a field silently degrades that one block to a placeholder — loudly in the
      console, invisibly to the user. If names must change, the manifests change with them, in the same PR.
    3. 
    
  3. Send business values only — no CSS, no coordinates, no __raw. See §5.
    4. 
    
  4. Send the eligibility facts the manifests already read. Verified across all 105 manifests:
      every one of the 12 gated actions reads exactly data.blocked (boolean) and
      data.canApprove (boolean); the only disabledReasonBinding in the corpus is
      data.blockReason (string, 8 actions); labelBinding points at a CTA string such as
      data.ctaLabel (26 actions). Omitting blocked/canApprove leaves the action
      enabled — see §8.
    5. 
    
  5. Implement the action endpoint and decide what it returns (§9 step 9).
    6. 
  


  
Contract rules the frontend guarantees

  
    
    
  • Extra fields are free. Unknown keys in data are ignored — no block binds to them.
    • 
    
  • Missing optional fields are safe. One placeholder, zero collateral damage.
    • 
    
  • Wrong-shaped fields are contained. A validator failure degrades that block only.
    • 
    
  • Exceptions are contained. A crash inside one block is caught by BlockErrorBoundary.
    • 
    
  • Array length is entirely yours. 0 rows renders an empty state; 500 rows paginates.
    • 
    
  • The UI never trusts when for security. Enforce authorisation server-side.
    •
